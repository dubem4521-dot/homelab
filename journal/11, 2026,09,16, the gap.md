## What Broke

### Port 5432 conflict

Tried to bring up the local compose while the server was also running Postgres. Port 5432 was already in use.

```
Error response from daemon: driver failed programming external connectivity
Bind for 0.0.0.0:5432 failed: port is already allocated
```

Fix: check `docker ps` first to see what is running. Stop the conflicting container, or map to a different host port.

### Postgres data directory permissions

First container start of the `db` service failed with:

```
initdb: error: could not change permissions of directory "/var/lib/postgresql/data"
```

The Postgres image runs as UID 999. The host mounted volume was owned by root. Postgres could not write to it.

Fix:

```bash
sudo chown -R 999:999 ./postgres-data
```

Or, more commonly, let Docker handle ownership by using a named volume instead of a bind mount:

```yaml
volumes:
  - beacon-db-data:/var/lib/postgresql/data
```

Named volumes are owned by Docker and do not have host filesystem permissions issues.

### `Base.metadata.create_all` running before DB was ready

First boot of the API container failed because Postgres was not yet accepting connections. The API tried to create tables and got "connection refused".

Fix: add `depends_on` with `condition: service_healthy` and a healthcheck on the database:

```yaml
db:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U beacon -h localhost -d beacon"]
    interval: 5s
    timeout: 5s
    retries: 10
    start_period: 10s
```

Then:

```yaml
api:
  depends_on:
    db:
      condition: service_healthy
```

Now the API waits until Postgres actually responds before starting.

### The SQLAlchemy two-model pattern

Spent a while confused about why I needed both an `ItemCreate` and an `ItemOut`. Both look similar. Why not one model?

The answer is important:

- `ItemCreate` is what the client sends. No `id`, no `created_at`.
- `ItemOut` is what the server returns. Includes `id` and `created_at`.

Mixing them would let a client try to set its own `id`. Bad. The separation is a security boundary.

Both are Pydantic models, distinct from the SQLAlchemy `Item` model which represents the database row itself. Three models, three jobs.

## Root Cause

Three separate issues, all common:

1. **Port allocation conflicts.** Always check `docker ps` before starting a new stack.
2. **Container user permissions on bind mounts.** Named volumes avoid this entirely.
3. **Startup race conditions.** `depends_on` with `service_healthy` is the fix.

Plus one conceptual thing: the request, response, and database models serve different purposes. Conflating them causes bugs.

---

## What I Learned

- **SQLAlchemy models are Python classes that map to database tables.** `Column` definitions become column definitions. Instance attributes become row values.
- **Three model layers is the standard pattern.** Request, response, and database models should be separate.
- **Pydantic handles request and response validation.** FastAPI reads the type hints and validates automatically.
- **`Base.metadata.create_all(bind=engine)`** creates missing tables on startup. Fine for development. Real projects use Alembic migrations.
- **Dependency injection with `Depends(get_db)`** is how FastAPI gives each request its own database session.
- **`status_code=201` for POST and `204` for DELETE.** Correct HTTP semantics matter.
- **Named volumes avoid host filesystem permission issues.** Use them unless you specifically need host access to the files.
- **Healthchecks plus `condition: service_healthy`** is the correct way to express service dependencies in compose.

## If This Happens Again

Adding Postgres to a FastAPI app:

1. Add to `requirements.txt`:
   ```
   sqlalchemy==2.0.36
   psycopg[binary]==3.2.3
   pydantic==2.9.2
   ```
2. Create `app/db.py`:
   ```python
   import os
   from sqlalchemy import create_engine
   from sqlalchemy.orm import sessionmaker, declarative_base

   DATABASE_URL = os.environ["DATABASE_URL"]
   engine = create_engine(DATABASE_URL)
   SessionLocal = sessionmaker(bind=engine)
   Base = declarative_base()
   ```
3. Create `app/models.py` with your SQLAlchemy models.
4. Create `app/schemas.py` with Pydantic request and response models.
5. In `main.py`, call `Base.metadata.create_all(bind=engine)` on startup.
6. Add a `get_db` dependency and use `Depends(get_db)` in route handlers.
7. Compose file with `db` service, healthcheck, and `depends_on` condition.

Test with the interactive `/docs` UI. Click through each endpoint.
