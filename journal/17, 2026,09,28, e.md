# Entry 17: 2026,09,28 - TJPork moves to Supabase, database and storage

**Duration:** ~4 to 5 hours, roughly 13:30 to 18:30
**Outcome:** TJPork running on Supabase Postgres and Supabase Storage. Data persists across container rebuilds.

---

## Context

TJPork had been containerized and running on the DietPi home server for a while. The app worked. Products displayed, admin could log in, orders could be placed.

Then I pulled a fresh Docker image and everything vanished.

Every product added since the last deploy. Every custom image upload. Every order. Every test account. All gone.

The reason: SQLite was storing the database inside the container's filesystem. Every rebuild produced a brand new empty container, and the database went with the old one.

This was the moment I realized the app could never be public like this. Not because the code was wrong, but because the storage layer was wrong. A real store needs data that survives deployments.

The Supabase migration was not a planned architectural upgrade. It was an urgent rescue mission to give the app real persistent storage before I could even think about sharing a link.

---

## What I Tried

1. Read Supabase's docs on hosted Postgres
2. Added Npgsql to the ASP.NET Core project, replacing the SQLite provider
3. Wrote a Supabase Storage client for product image uploads
4. Set up the connection string in `.env`
5. Wrote an automated database seeder that creates tables and inserts defaults on first boot
6. Pushed to GitHub and let the CI pipeline build and deploy
7. Chased runtime errors in the deployed container

---

## What Broke

Four distinct problems. All detailed in the next entry. Summary:

1. **IPv6 only connection string.** Supabase's direct database endpoint is IPv6 only. Docker bridge networks default to IPv4. The connection timed out from inside the container.
2. **`relation "AspNetRoles" does not exist`.** Supabase ships with internal system tables. Entity Framework Core saw those and assumed the app's tables existed too. Skipped creating them. The seeder then crashed.
3. **Silent 403s on image upload.** The anonymous Supabase Storage key cannot write. Row Level Security blocked uploads. No error surfaced in the app.
4. **`Cannot write DateTime with Kind=Unspecified`.** Checkout crashed when placing an order. HTML date inputs send unspecified DateTime. PostgreSQL demands UTC.

Each one required a separate fix. Together they made this the longest debugging session in the project so far.

---

## Root Cause

Two layers of causes.

**Immediate:** moving from SQLite to Postgres is not just a driver swap. The two databases have different type systems, different schema detection, different permission models. Each difference produced a bug.

**Deeper:** the app was never designed for persistence. SQLite inside a container works for development. It cannot survive a rebuild. Once the app became a real deployed service, the storage model had to change.

The migration exposed both: the app needed a real database, and the app needed to handle Postgres's stricter rules.

---

## What I Learned

- **SQLite in a container is a footgun.** Every `docker compose down` can take the database with it. Fine for prototypes, wrong for anything real.
- **Supabase's direct database URL is IPv6 only.** Use the connection pooler instead. The pooler supports IPv4 and works inside Docker.
- **Supabase ships with internal system tables.** Entity Framework's `HasTablesAsync()` check is not safe against a database that already contains someone else's schema. Check for your own tables specifically.
- **Row Level Security is on by default.** The `anon` key cannot write files to Storage. You need the `service_role` key for server side uploads.
- **PostgreSQL `timestamptz` is strict.** It refuses `DateTimeKind.Unspecified`. Either enable legacy timestamp behavior or normalize to UTC before saving.
- **Cloud storage changes the shape of image handling.** No more local file paths. Every uploaded image becomes a public URL that gets stored in the database.
- **The bugs only appear after deployment.** Local builds looked fine. The Docker container was where the failure surfaced. Testing in the container is not optional.

---

## The Architecture Change

**Before:**

```
ASP.NET container
  - SQLite file inside the container filesystem
  - Uploaded images stored in a Docker volume
```

Rebuild the container, lose everything.

**After:**

```
ASP.NET container
  - Connects to Supabase Postgres via connection pooler
  - Uploads images to Supabase Storage
  - Stores public image URLs in the database
```

Rebuild the container, lose nothing. The container becomes stateless.

The `DATABASE_URL` environment variable is the switch. If it is set, the app uses Postgres. If not, it falls back to local SQLite for offline development on a laptop.

---

## The Seeder

Previously, someone had to run SQL scripts manually to set up a new database. That does not scale, especially for a cloud database.

Wrote `DatabaseSeeder.cs` that runs on app startup:

1. Checks whether the app's own tables exist.
2. If not, creates them via Entity Framework migrations.
3. Inserts default products, categories, and an admin user.
4. Logs what it did.

This means deploying to a fresh database requires no manual steps. Push, deploy, the app bootstraps itself.

---

## The Storage Client

Uploaded product images used to save to a local file path. That broke with cloud hosting. Rewrote the upload path:

1. Admin picks a file in the browser.
2. ASP.NET receives the file.
3. The Supabase Storage client uploads it to the `tjpork-images` bucket.
4. Supabase returns a public URL.
5. The URL is saved in the database, next to the product.

Public images are readable by anyone with the URL. Writes require the `service_role` key, which stays on the server.

## If This Happens Again

Migrating an app from local storage to a cloud database:

1. **Pick the right connection string.** For Supabase, use the pooler URL, not the direct URL. Pooler supports IPv4.
2. **Test schema detection.** Do not assume EF Core's `HasTablesAsync()` works on a database that has pre-existing tables. Check for your specific tables by name.
3. **Verify storage permissions.** Read the docs for the storage service you use. Which key can write, which can read. Test from the actual server, not just from localhost.
4. **Watch for type system differences.** SQLite is loose. PostgreSQL is strict. Dates, times, UUIDs, booleans, enums, all behave differently.
5. **Normalize dates to UTC before saving.** If your framework has a "legacy timestamp behavior" switch, flip it as a temporary fix, but the real fix is sending UTC.
6. **Always test in the container.** Local testing does not catch Docker network issues, DNS resolution problems, or environment differences.
