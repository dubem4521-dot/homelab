## Bug 1: Docker could not reach Supabase

**What happened:** The initial connection string used Supabase's direct database endpoint. It worked fine from my laptop. It failed from inside the Docker container on the DietPi server.

**Symptom:** Connection timeouts. The container would start, try to connect to the database, and hang. Eventually the connection attempt failed and the app crashed.

**Investigation:**

From the container's shell:

```bash
docker exec -it tjpork-web bash
nslookup db.fgvqlgeivtduxhummedq.supabase.co
```

The DNS lookup returned only an IPv6 address. No IPv4.

The default Docker bridge network on Linux does not route IPv6. The container could resolve the hostname but could not actually connect.

**Root cause:** Supabase's direct database endpoint is IPv6 only. Docker's default bridge network is IPv4 only. They cannot talk.

**Fix:** Use Supabase's connection pooler instead. The pooler listens on both IPv4 and IPv6.

Changed the connection string from:

```
Host=db.fgvqlgeivtduxhummedq.supabase.co;Port=5432;...
```

To:

```
Host=aws-0-eu-central-1.pooler.supabase.com;Port=5432;...
```

The pooler also has a benefit: it handles connection pooling on Supabase's side, which matters for a container that restarts a lot.

**Lesson:** Always use the connection pooler for Supabase when connecting from a container. The direct connection is for local development or for services running on IPv6-capable networks.

## Bug 2: `relation "AspNetRoles" does not exist`

**What happened:** After fixing the connection string, the container started and immediately crashed during database seeding.

**Symptom:**

```
Npgsql.PostgresException (0x80004005): 42P01: relation "AspNetRoles" does not exist
   at Microsoft.EntityFrameworkCore.Query.Internal.SingleQueryingEnumerable`1.AsyncEnumerator.MoveNextAsync()
fail: Program[0] An error occurred while seeding the T&JPork database.
```

**Investigation:**

Entity Framework Core has a method, `HasTablesAsync()`, that checks whether a database is blank. If the database has no tables, EF Core creates the schema. If it has tables, EF Core assumes the schema already exists and skips creation.

Supabase's `postgres` database comes pre-loaded with internal system tables and extensions. When my app booted, EF Core looked at the database, saw those internal tables, and concluded "tables exist, do not create."

Then one millisecond later, the seeder tried to insert an admin user into `AspNetRoles`, which had never been created.

**Root cause:** `HasTablesAsync()` is too broad. It checks for any table, not specifically for the app's tables. On a shared or pre-provisioned database, the check returns the wrong answer.

**Fix:** Bypass `HasTablesAsync()` entirely. Query `information_schema.tables` for a specific table name the app needs.

```csharp
// Instead of:
// if (!await dbContext.Database.EnsureCreatedAsync())

// Do:
var sql = @"
    SELECT EXISTS (
        SELECT 1 FROM information_schema.tables
        WHERE LOWER(table_name) = 'aspnetroles'
    )";

var exists = await connection.ExecuteScalarAsync<bool>(sql);
if (!exists)
{
    await dbContext.Database.MigrateAsync();
    // ...then seed
}
```

Now the check is specific. It asks: does the app's own `AspNetRoles` table exist? If no, create everything. If yes, skip creation and proceed to seeding.

**Lesson:** Never trust a generic schema detection method on a database you did not create. Check for your own tables explicitly.

**Time spent:** This was the longest of the four bugs. Roughly 90 minutes. The error message was clear, but the reason behind it was not. It took a while to connect "Supabase has system tables" with "EF Core thinks the schema exists."

## Bug 3: Uploaded images did not appear on Supabase

**What happened:** Product image uploads in the admin panel stopped working after the migration.

**Symptom:** The upload appeared to succeed in the UI. The image just was not there afterward. The Supabase Storage bucket stayed empty. No error message appeared in the browser. No error appeared in the app logs either.

**Investigation:**

Checked the Supabase dashboard for the storage bucket. Nothing. Checked the browser console. Nothing. Checked the ASP.NET logs.

Ran the upload manually from inside the container:

```bash
docker exec -it tjpork-web bash
# Trigger the upload, watch the log
```

The client was returning a `403 Forbidden` error. The app was catching that error and simply logging it as a silent failure.

**Root cause:** Supabase Storage uses Row Level Security by default. The `anon` public API key can read public files but cannot write them. Server-side uploads need the `service_role` key.

**Fix:** Two changes.

1. Changed the `.env` file to use the `service_role` key instead of the `anon` key for server-side operations.

```
SUPABASE_KEY=<service_role-key>
```

2. Made the `tjpork-images` bucket public so customers' browsers can view product images without authentication.

**Lesson:** Cloud storage services have layered permissions. Reading and writing can require different keys. Check the docs and test each operation separately. Silent failures are the worst kind, always log the actual HTTP status code.

## Bug 4: Checkout crashed when placing an order

**What happened:** Everything worked. Products loaded. Cart worked. Then clicking "Place Order" crashed with a 500 error.

**Symptom:**

```
Microsoft.EntityFrameworkCore.DbUpdateException: An error occurred while saving the entity changes.
---> System.ArgumentException: Cannot write DateTime with Kind=Unspecified to PostgreSQL
type 'timestamp with time zone', only UTC is supported.
at Npgsql.Internal.Converters.DateTimeConverterResolver`1.Get(DateTime value, ...)
at TJPork.Infrastructure.Services.OrderService.CreateOrderAsync(...)
in OrderService.cs:line 110
```

**Investigation:**

The stack trace pointed to `OrderService.CreateOrderAsync`. Looking at the code, an order's `DeliveryDate` was being saved directly from a form field.

The form field was an HTML date input:

```html
<input type="date" name="deliveryDate" />
```

When the user submits, the browser sends `"2026-10-02"`. ASP.NET Core binds this to a C# `DateTime` with `Kind = DateTimeKind.Unspecified`. It has no time zone information at all.

SQLite accepted this. It stored dates as loose text. No validation.

PostgreSQL's `timestamptz` column type refuses any DateTime that is not explicitly marked UTC. The Npgsql driver threw an exception before the save even reached the database.

**Root cause:** SQLite is permissive. PostgreSQL is strict. HTML date inputs produce timezone-agnostic values. Npgsql 6 and later enforce UTC.

**Fix:** Three changes.

1. Enabled PostgreSQL's legacy timestamp behavior as a safety net:

```csharp
AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true);
```

This tells Npgsql to accept unspecified kinds without crashing. It is a temporary fix, not a cure.

2. Normalized the delivery date to UTC before saving in `OrderService.cs` and `CheckoutController.cs`:

```csharp
var utcDeliveryDate = DateTime.SpecifyKind(
    model.DeliveryDate,
    DateTimeKind.Utc);
```

3. Added user-facing error handling so a failed checkout shows a friendly banner instead of a raw 500 error page.

**Lesson:** Date and time handling is the most common cross-database portability issue. SQLite does not care. PostgreSQL cares a lot. Always be explicit about time zones at the boundary, and always convert to UTC before saving.

**Bonus lesson:** The green Order Confirmation page with a real order number like `TJP-2026-XXXXXX` was the eureka moment. Seeing that succeed after hours of debugging was worth every minute.

## The Docker Log Trap

A meta bug that made all four harder to find.

When running:

```bash
docker compose logs --tail=20 tjpork-web
```

The last twenty lines were always generic ASP.NET startup output. The actual root cause was buried higher up in the log, invisible to `--tail=20`.

ASP.NET Core stack traces are enormous. A single exception can produce 50+ lines. `--tail=20` cut off the important part.

**Fix:** Tail more lines, or grep for the exception:

```bash
docker compose logs --tail=200 tjpork-web
docker compose logs tjpork-web | grep -A 20 "Exception"
```

**Lesson:** When looking for a specific error in container logs, grep for the exception type instead of tailing a fixed number of lines. Or follow the log live:

```bash
docker compose logs -f tjpork-web
```

And watch from the moment the failure occurs, not after.

## What I Learned, All Together

- **SQLite is loose. PostgreSQL is strict.** Migrations always surface the differences.
- **Cloud databases come with baggage.** Pre-existing system tables. Default security rules. IPv6-only endpoints. None of these are on your laptop.
- **Silent failures are the worst failures.** Always log the actual HTTP status code. The `anon` key's 403 was invisible until I looked for it manually.
- **`--tail=N` is a trap for stack traces.** Grep for the exception type instead.
- **Date and time handling will bite you.** Always be explicit about UTC.
- **Test in the container.** Local builds catch nothing about deployment.
- **Each fix reveals the next problem.** This is normal. Expect it, plan for it, budget time for it.
