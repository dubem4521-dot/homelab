## Context

TJPork was fully migrated to Supabase earlier in the day. Database working, images working, orders working. The app itself was ready.

But it was still only reachable inside the home network. Nobody outside could open it.

Time to expose it. Before doing that, I wanted a review of the infrastructure. Wanted a second set of eyes on the Dockerfile, the compose files, and the CI workflows before putting them behind a public URL.

That review surfaced several issues and one structural problem. Then I picked the deploy path.

## The Infrastructure Review

### What was found

The reviewer could see the Dockerfile, the repo's `docker-compose.yml`, and the `.github/workflows/` folder, but GitHub blocked commit history and source folders. So the review covered the infrastructure side only.

**What was already good:**

- The Dockerfile is a proper multi stage build. Restores dependencies before copying source, so Docker caches the restore layer. Uses the smaller ASP.NET runtime image for the final stage, not the full SDK.
- The project layout is clean. `src/TJPork.Core`, `src/TJPork.Infrastructure`, `src/TJPork.Web`, plus a `tests/TJPork.Tests` project.
- `.env.example` is committed and the real `.env` is gitignored. Secrets flow through environment variables like `SUPABASE_KEY`, not hardcoded.

**What needed fixing:**

| Finding | Severity | Notes |
|:--------|:---------|:------|
| `version: '3.8'` obsolete | Low | Compose ignores it, warns |
| Redis exposed on port 6379 | Medium | Should be internal or bound to 127.0.0.1 |
| MailHog in the production compose | High | Real customers would never get emails |
| `:latest` tags on all images | Medium | Non reproducible builds |
| Container runs as root | Low | Could add a non root user |
| No `HEALTHCHECK` | Low | Nice to have |
| No `.dockerignore` | Low | Bloats the build context |
| No README | Medium | Repo has no About text |
| Tests exist but no CI runs them | Medium | `dotnet test` should be in the pipeline |

### The real finding: repo and server had drifted

The repo's `docker-compose.yml` and the server's `docker-compose.yml` had diverged. They started from the same file but had drifted apart through months of edits on the server.

The repo version had:
- `ASPNETCORE_ENVIRONMENT=Production` set
- MailHog for catching emails
- Redis exposed on the host
- `:latest` tags

That is a development setup wearing a production label. Real customers would never receive emails because MailHog catches them and discards them.

The server version had:
- Port bound to `127.0.0.1:5000`, only reachable from the host
- No Redis or MailHog at all
- Real environment values from `.env`

The server version was already the more correct one. The repo had the weaker version.

**This is the actual problem.** If I had to rebuild the server from scratch, I would not know which compose file to trust. The repo says one thing, the server runs another, and nothing keeps them in sync.

### What was missing on the server

One important line for running behind a proxy:

```
ASPNETCORE_FORWARDEDHEADERS_ENABLED=true
```

Without it, when a visitor arrives via HTTPS through a tunnel, the app sees HTTP and builds wrong URLs. Login redirects loop. This becomes visible only when testing from outside.

### The fix plan

1. **Split compose files in the repo.** `docker-compose.yml` becomes the dev file. `docker-compose.prod.yml` is added and matches the server.
2. **Add `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` to the server compose.**
3. **Run tests in CI.** Add a job before the build that runs `dotnet test`.
4. **Pin image versions.** Replace `:latest` with specific tags.
5. **Commit the server compose to the repo** as the prod file, so the two cannot drift again.

Most of these are still to do. The immediate priority was getting the site reachable. So item 2 was done today, and the rest are queued.

## Choosing the Expose Method

Four options considered:

| Option | Verdict |
|:-------|:--------|
| Netlify rewrite | Rejected. Wrong runtime for ASP.NET, would be a full rewrite. |
| Open router port + port forward | Rejected. Risky without a reverse proxy in front. |
| Cloudflare Tunnel | Deferred. Needs a domain name I do not own. |
| **Tailscale Funnel** | **Chosen.** Free, no domain, uses existing Tailscale setup. |
| Move to Cloud Run or Azure | Deferred. Good for a future cloud learning exercise. |

Funnel won because:
- No router ports to open
- No domain name needed
- Uses the same Tailscale account already running on the server
- One command to start
- Free

The trade off is the URL ends in `.ts.net` instead of a custom domain. Acceptable for now.

## The Forwarded Headers Setting, Explained

This was the one line change and it is worth understanding why it matters.

When a visitor opens the public URL, they use HTTPS. Encrypted. Proper.

But the request travels:

```
Visitor, HTTPS
   ↓
Tailscale public servers
   ↓
Private tunnel, encrypted
   ↓
Server, arrives on the private interface, plain HTTP
   ↓
Docker port mapping
   ↓
ASP.NET container, sees HTTP
```

By the time the request reaches the app, it looks like HTTP. The app has no idea the original visitor used HTTPS.

This becomes a problem in three places:

- **Redirects.** If the app generates a redirect, it uses `http://`. The browser tries to load an HTTP URL from an HTTPS page. Modern browsers block this. Or the redirect loops.
- **Absolute URLs.** Login links, password reset emails, callback URLs. All become `http://` and either break or get flagged as insecure.
- **Cookies.** Secure cookies are refused over plain HTTP. Sessions break.

The setting `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` tells ASP.NET to trust forwarding headers. Tailscale Funnel sends a header that says "the original request was HTTPS." With the setting enabled, ASP.NET reads that header and behaves as if the request came over HTTPS all along.

Without it, you get login loops that look like the site is broken.

## The Full Path a Visitor Takes

```
1.  Visitor types the .ts.net URL into their browser
2.  Browser connects to Tailscale's public servers over HTTPS
3.  Tailscale sends the request through an encrypted tunnel to the DietPi
4.  The funnel forwards it to port 5000 on the server
5.  Docker forwards from port 5000 to port 8080 inside the container
6.  ASP.NET reads the forwarded headers, sees "HTTPS, host=the .ts.net URL"
7.  The app queries Supabase for data and images
8.  The response HTML travels back through the same path
9.  The visitor sees the page
```

Ten hops. All invisible. All running on hardware I own, on my home internet connection, without any open router ports.

## The Command Sequence

On the server:

```bash
# 1. Edit the compose file
cd /srv/share/docker/tjpork-app
nano docker-compose.yml

# 2. Add under environment:
#    - ASPNETCORE_FORWARDEDHEADERS_ENABLED=true

# 3. Restart
docker compose up -d
docker compose logs -f tjpork-web
# Ctrl+C to exit when satisfied

# 4. Start the funnel
sudo tailscale funnel --bg 5000

# 5. Check the status
tailscale funnel status

# 6. Test from mobile data
```

The `--bg` flag runs the funnel in the background. Without it, the funnel stops when the SSH session closes.

## What I Learned

- **Tailscale Funnel is the shortest path from "runs locally" to "publicly reachable."** No domain, no port forwarding, no DNS setup. One command.
- **Forwarded headers are required behind any proxy.** Tunnels, load balancers, nginx, Cloudflare, all the same. The app cannot tell what the original request looked like unless the proxy tells it.
- **Test from outside.** A local test would never have caught the redirect issue. Mobile data was the only way to be sure.
- **`tailscale funnel --bg`** keeps the funnel running after you close the terminal. The `--bg` flag is the important part.
- **`tailscale funnel status`** shows what is currently exposed.
- **Repo drift is real.** Server compose and repo compose had diverged. The fix is to commit the running version to the repo and use it as the source of truth.
- **Split dev and prod compose files.** Dev has MailHog, exposed Redis, debug settings. Prod has real config, tight ports. They should not share a file.

## If This Happens Again

Exposing a local service with Funnel:

1. **Verify the service runs locally first.**
   ```bash
   curl -I http://localhost:5000
   ```
2. **Add forwarded headers if the app is behind any proxy.** For ASP.NET, `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`. For nginx, `proxy_set_header X-Forwarded-*`. For other apps, look up the equivalent.
3. **Restart the service after config changes.** Use `docker compose up -d`, which recreates the container. A plain restart does not always pick up env var changes.
4. **Start the funnel.**
   ```bash
   sudo tailscale funnel --bg 5000
   ```
5. **Check status.**
   ```bash
   tailscale funnel status
   ```
6. **Test from outside the network.** Mobile data is the fastest check.
7. **If redirects loop or links break:** the forwarded headers setting is missing or wrong.
