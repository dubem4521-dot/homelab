# Entry 14: 2026,09,22 — Pi-hole to Docker migration

**Duration:** ~4 hours
**Outcome:** Pi-hole running in a container. Config migrated. DNS working.

---

## Context

Pi-hole was installed natively on 2026,09,07. It had been running fine for two weeks. But native installs have problems:

1. Updates require `apt upgrade` on the whole system
2. Port conflicts are hard to reason about
3. No isolation from other services
4. Harder to move to a different machine later

Time to containerize it.

---

## What I Tried

1. Backed up `/etc/pihole` to `/srv/share/docker/pihole`
2. Stopped the native `pihole-FTL` service
3. Stopped and disabled `lighttpd`, the native web server
4. Wrote a `docker-compose.yml` using `pihole/pihole:latest`
5. Mounted the backup folder as `/etc/pihole` in the container
6. Ran `docker compose up -d`

---

## What Broke

### Port 80 was already in use

First attempt to start the container failed:

```
Error response from daemon: driver failed programming external connectivity
Bind for 0.0.0.0:80 failed: port is already allocated
```

The `beacon-dashboard` container was already on port 80. So Pi-hole could not have it.

Fix: move Pi-hole's web UI to host port 8080.

```yaml
ports:
  - "8080:80/tcp"
```

Tried again.

### Pi-hole v6 changed its internal web port

Even with the mapping fixed, Pi-hole was still not responding on `http://<host>:8080/admin`.

Checked the container logs:

```
INFO: Web server ports:
INFO:   - 0.0.0.0:8089 (HTTP, IPv4, OK)
```

Pi-hole v6 runs its web UI on port **8089** inside the container. Not 80. Not 8080. 8089.

The compose file needed:

```yaml
ports:
  - "8080:8089/tcp"
```

Now the host port 8080 maps to the container's internal 8089, where Pi-hole is actually listening.

**Lesson:** always check container logs to see what port an app is actually using. Do not assume from the docs.

### The Tailscale firewall blocked port 8080

Local access worked. Remote access did not:

```
curl: (7) Failed to connect to 100.x.x.x port 8080
```

The diagnostic:

```bash
sudo iptables -L -n | grep -E 'tailscale|100\.'
```

Output showed:

```
DROP       all  --  100.64.0.0/10        0.0.0.0/0
ACCEPT     all  --  100.x.x.x             0.0.0.0/0
DROP       all  --  100.64.0.0/10        0.0.0.0/0
```

The iptables rules were dropping the whole Tailscale range, allowing only one specific IP. That specific IP was the node's own Tailscale address. Nothing from outside could reach it.

Fix:

```bash
sudo iptables -I INPUT 1 -s 100.64.0.0/10 -j ACCEPT
```

Then persist:

```bash
sudo apt install iptables-persistent
sudo netfilter-persistent save
```

### The SQLite WAL warning

Pi-hole logs showed:

```
ERROR: SQLite3: recovered 233 frames from WAL file /etc/pihole/pihole-FTL.db-wal (283)
```

**What it means:** The previous native install was not shut down cleanly. Its SQLite database had pending writes in a write ahead log. On first container start, SQLite replayed those writes to bring the database back to a consistent state.

**Result:** No data lost. 233 pending writes recovered.

**Lesson:** Stop services gracefully whenever possible. `systemctl stop <service>` instead of killing the container.

### The container healthcheck is slow

First container start showed `Up X seconds (health: starting)` for a while. The Pi-hole image has a healthcheck that takes about 30 seconds to pass. During that window, the container is functional but marked unhealthy.

Not a bug. Just expected behavior. Wait for `(healthy)` before assuming something is wrong.

---

## Root Cause

Four separate issues, all common on native to Docker migrations:

1. **Port conflicts.** Always check `docker ps` before choosing a host port.
2. **Application internal ports change between versions.** Pi-hole v6 moved from 80 to 8089.
3. **Tailscale iptables rules block ports by default.** Same fix as before.
4. **SQLite recovery is normal** after an unclean shutdown. Not an error, just a log entry that uses the word ERROR.

---

## What I Learned

- **Always check `docker ps` for port conflicts.** `docker ps --format 'table {{.Names}}\t{{.Ports}}'` is a good one liner.
- **Check container logs to find the actual listening port.** Do not trust the docs. Look at the output.
- **Port mappings are host:container.** Left of the colon is the host side, right is the container side.
- **`docker exec <container> ps aux`** shows what processes are running inside. Useful for confirming the web server is actually up.
- **Tailscale firewall rules** drop the whole tailnet range by default. Explicitly allow it or specify the correct IPs.
- **SQLite WAL recovery** is normal and safe. The `ERROR` prefix is misleading.
- **Named volumes are safer than bind mounts for databases.** SQLite especially can corrupt on network filesystems.
- **Healthchecks can take time.** Wait for `(healthy)` before assuming the container is broken.

## If This Happens Again

Migrating a native service to Docker:

1. **Back up the config.**
   ```bash
   sudo cp -r /etc/<service> /srv/share/docker/<service>/config
   ```
2. **Stop the native service.**
   ```bash
   sudo systemctl stop <service>
   sudo systemctl disable <service>
   ```
3. **Check for port conflicts.**
   ```bash
   docker ps --format 'table {{.Names}}\t{{.Ports}}'
   sudo ss -tlnp | grep -E ':<port>'
   ```
4. **Write the compose file.**
5. **Start the container.**
6. **Check the logs for the actual listening port.**
   ```bash
   docker logs <container> --tail 30
   ```
7. **Test from a client.**
   ```bash
   curl -I http://<host>:<port>
   ```
8. **Fix iptables if remote access fails.**
